# iNaturalist multi-location observations

## User

Look at https://github.com/IMERSS/inat-components - can it be configured to fetch observations from multiple iNaturalist location ids, e.g. the ones attached to this project https://www.inaturalist.org/projects/lost-plants-of-the-saanich-peninsula

## Claude

I'll check the repo's code and the project's places.

Now the project's places.

Short answer: **not officially, but it works in practice with no code changes**, because of how the code builds its requests.

**What the code does.** Every API call in `shared/api/*.ts` (recent observations, common taxa, favourites, and the three stats calls) just drops the place value into the URL as `&place_id=${placeId}`. The place config is `{ id, str }`, where `str` is only used to name the cached JSON files. `id` is typed as a `number` in TypeScript, but nothing checks or converts it at runtime.

**Why that's enough.** The iNaturalist v1 API accepts a comma-separated list for `place_id` and returns observations from any of those places, without duplicates where places overlap. So in the `inat-components-utils` config you can write:

```js
places: [
  { id: "12345,67890,13579", str: "saanich-lost-plants" }
]
```

The utils script then fetches and writes `…-saanich-lost-plants-recent.json` and the other files, and the standalone panel reads them through `str`. You can do the same in the standalone panel's `place` setting when it fetches live. If you build the TypeScript yourself, you'd need to widen `ItemConfig.id` to `number | string`, or add a cast, to keep the compiler happy.

**Caveats:**
- I couldn't open the project page or the iNat API from here; both were blocked. So I can't give you that project's actual place IDs. You can see them under the project's requirements ("Place(s)"), or at `api.inaturalist.org/v1/projects/lost-plants-of-the-saanich-peninsula` under `search_parameters`.
- A collection project usually has more rules than places, such as taxa, dates, quality grade, or excluded places. A place list only matches the project's results if the places are the only filter. Taxa are handled separately through the `taxon` setting, which takes a single ID.
- If you want results that match the project exactly, the cleaner option is a small patch that adds an optional `projectId` and appends `&project_id=…` to those six URLs. That's about a 10-line change, and I can write it if that's useful.

## Claude

That's the project's API record. It has 29 places, 68 taxa and a quality filter of research + needs ID, and the config can reproduce all three without changing the code.

**Places.** As covered above, these can be joined with commas into one `place_id`.

**Taxa.** `taxonId` goes into the URLs the same way (`&taxon_id=${taxonId}`), and iNat also accepts a comma-separated list there. So the 68 taxa can be passed as one string too.

**Quality grade.** Four of the six calls already send `verifiable=true`, which is exactly research + needs ID. The two that don't are recent observations and the stats call that fetches the latest observation, so they could also pick up casual observations. To match the project exactly, add `&verifiable=true` to those two URLs (`recent-observations.ts` and `getObservationSummary` in `summary.ts`).
